- Activation started 2026-11-11 16:25:10 CST with the queue empty, after a verified code and candidate build. Backup: `/var/backups/pro6000d-training/monthly-release-20261111T082510.351713Z`. Staged platform backup: `/var/backups/pro6000d-training/staged-upgrade-20261111T075224.353035Z`.

The backend became ready without restarting or rolling back the scheduler. At 16:46 CST release attestation, controller readiness, four-device inventory and the administrator API's enforcement, selected-tier and application readiness were verified. The original failure record is preserved; subsequent verified state is recorded separately in `operator-verification.json` inside the activation backup.

A separate important-tier platform job obtained one GPU, initialized CUDA with one visible device, passed the live selector audit, completed successfully, and its generation had a durable `RELEASE2` record and increased important-tier usage. The temporary hold was confirmed cancelled, both platform test jobs finished naturally, and the direct pending test expired without allocation. The complete root-only receipt is `live-smoke-repeat.json` in the activation backup. Earlier smoke run's overly broad node-field matcher was corrected; its receipt remains preserved.
- UI updated 16:45 CST, without restarting Slurm, to show current or unconfirmed quota status accurately. UI backup: `/var/backups/pro6000d-training/monthly-ui-f84206e-20261111T084500.467410Z`. Three installed UI file hashes matched the committed files. Runtime services remained active and the queue was empty after the smoke test.
- Slurm's NVML enumeration differed from device-minor order, so this release uses explicit `/dev/nvidia[0-3]` with `AutoDetect=off`; NVML GPU/CPU affinity and GPU link topology are not provided to the scheduler under this configuration. Initial failed cutovers and their preserved empty initial ledgers are documented in the first- and second-attempt records.
- Rollback was not performed after admission opened, because stopping the controller could affect newly running jobs. If rollback is needed later, first inspect live jobs and ledger state, allow running work to finish, and review the saved Slurm configuration, `gres.conf`, systemd unit and database backup. Do not overwrite the live ledger or restore an old database over new usage.
