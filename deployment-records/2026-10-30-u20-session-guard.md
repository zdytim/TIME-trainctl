# u20 training-session isolation guard

- Target and time: `u20-Z790-S-DDR4`, 2026-10-30 approximately 22:10–22:11 Asia/Shanghai. Guard code commit `90fa24a`; common-session fixture commit `9aed697`; rollout script commit `34c95ac`. The commits were pushed to `u20-slurm19` before use.
- Changed only `/usr/local/libexec/pro6000d-session-guard` from SHA-256 `d383a6b0dfcfceabd1f3d1ca0a276e2b852bbb54edcb5ed0da81f6d1c7fa87b7` to `274a70e98183d0055d063c19f4eb24a0569d883788fe2f98bcf2545417a0ecab`. The new guard requires an ordinary enrolled training user's actual cgroup v1 devices hierarchy to be inside their closed user slice and to deny the currently observed NVIDIA character devices. Administrator accounts are exempt. PAM configuration, Slurm, controller, GPU devices and existing processes were not replaced or restarted.
- Backup: `/var/backups/time-session-guard-90fa24a.piiX7BW4/session-guard.before`, inside a root-only directory. The rollout restores this file automatically if its post-change checks fail. In a disposable container with a deliberately failing PAM fixture, the rollout restored the old guard and confirmed its hash. No rollback was needed on u20; manual rollback, if later required, must restore the root-owned 0755 backup to the same target and independently verify PAM and service access.
- Validation: immediately before replacement Slurm had no queued or running jobs and all four services were active. After replacement, a temporary PAM service using the host's actual `common-session` accepted a `timzhang` session, a deliberately failing session module was rejected, and logind's session set returned to its original state. As in the prior fixture, `pam_close_session` returned 6 after the deliberately rejected open. A separate check denied `timzhang` from outside his slice and accepted the `u20` administrator. The live guard's digest matched the candidate; Cockpit, Slurm and the training backend remained active; the host queue was empty and Sunshine's existing GPU process remained. No complete real SSH or Cockpit authentication was performed as part of this rollout.
- Limitations: the guard deliberately fails closed if the target's cgroup v1 devices hierarchy, systemd status or NVIDIA device list cannot be checked, so an unavailable driver or future cgroup v2 migration needs a reviewed adaptation. This change does not restrict privileged accounts, unenrolled non-training accounts, a device appearing after session verification, or processes outside the protected login/session paths. Device-node recreation can still reset ACLs. The monthly quota controller remains staged and disabled.
