# Root-owned quota witness candidate

This staged candidate adds a separate append-only witness outside Slurm's service-owned state directory. A root launcher opens and locks an existing private root-owned witness before executing `slurmctld`; the descriptor survives the privilege drop. Each WAL event is acknowledged only after the WAL, checksum checkpoint and witness record have each been fsynced. On restart the controller requires the witness's last sequence and digest to match the local WAL/checkpoint and fails closed on missing, invalid, stale or inconsistent state. A fresh-only initializer refuses to replace existing state or initialize a nonempty WAL. These files are not installed, and quota enforcement stays disabled.

The root-owned witness protects against an ordinary restoration of only Slurm's service-owned ledger and checkpoint to a matching older pair. It is not an independent host or immutable storage: an administrator, a compromised controller holding its writable descriptor, or a whole-filesystem rollback can still alter or roll back all evidence. It does not resolve migration of prior usage, unsupported job shapes, crash ambiguity between three fsyncs, or the full power-loss and runtime security model. A crash between writes intentionally requires operator reconciliation and must not silently recreate state. The initializer only accepts an exactly empty ledger and is not evidence that historical usage may be reset. Before deployment, review process/descriptor inheritance, systemd integration, service-user trust, storage ordering, offline recovery and real workload safety.

The first isolated `20652b1` run started Slurm but the witness was unavailable. Source inspection found Slurm 19 explicitly closes every inherited descriptor above 2 in `main`, before dropping privileges. The follow-up `preserve-witness-fd.patch` retains only a descriptor that has the expected root-owned, private regular-file metadata and append/read-write flags, and sets close-on-exec before other programs can inherit it. The controller still checks the full witness contents and lock later. This follow-up is a source candidate and requires a clean rebuild plus isolated descriptor, rollback and crash validation; no production service was modified.

On 2026-10-30, the clean `0dc0b40` release-layout candidate built on u20 with controller SHA-256 `6868c36ae16af07cabb0f15cf6101b5f50a0063742eecfaf599250eb622f4613`. Networkless container tests used a private root-owned witness, separate container-only ledger and fake GPUs. A healthy ledger started and accounted a job. Restoring both ledger and checkpoint to an older, mutually matching empty version while preserving the later witness caused the quota interface to fail closed and left a new GPU request pending without a node. A missing witness also failed closed. A running fake-GPU job and accounting survived an abrupt controller process kill and restart. A UID 1001 fixture job stayed unallocated at exhaustion, then started and completed after the real candidate broker granted credit; an additional isolated broker process-exit reconciliation passed. With four fake GPUs and four GPU-seconds left, an existing job continued beyond exhaustion and finished while a second remained unallocated. An initial overage run with only one fake GPU showed `Resources` rather than the quota reason and was not counted. Fresh witness initialization was checked in separate private tmpfs, including refusal to overwrite or initialize a nonempty ledger and denial of unprivileged read access. No production code, service, device or job was modified.

These results are synthetic process-level evidence, not tests of physical power loss, full-filesystem rollback, Slurm's live cgroup plugins, all descriptor-leak paths, production history migration or real GPU scheduling. The failure cases conservatively paused a mixed queue and could show a stale pending reason. No live witness has been initialized and the monthly gate remains disabled.

The same `0dc0b40` controller was additionally launched without `-D` in a networkless container using the root witness launcher and Slurm's normal daemonization. Its daemon ran as the Slurm service UID, responded to `scontrol ping` and returned an eligible quota response over its private socket, showing that the witness descriptor survived daemonization and the privilege drop. The first container attempt lacked a hostname mapping and could not resolve its synthetic controller host; that attempt is not a pass. After adding a container-local mapping the check passed. This is not a systemd integration or production deployment check.
