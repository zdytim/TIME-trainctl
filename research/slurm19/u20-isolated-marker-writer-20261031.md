# Locked grant marker writer in an isolated running-job scenario

On 2026-10-31, image `time-marker-write:61ccd08` (SHA-256 `e3c4fd86dbaa7870558bd81df887ac6951bf406560ccf452c0d4e9c7f6ffce48`) ran the committed experimental marker writer in two separate networkless disposable containers. Each had private Slurm state and witness tmpfs, a private real broker SQLite database, a synthetic GPU, staged controller `7a06cff`, and the stock u20 node daemon; no host GPU device or live state was mounted.

In both `wal_ahead` and `witness_behind` cases, a running synthetic-GPU job and pending SQLite approval survived the controller being killed and a deliberately simulated marker lag. Quota was unavailable until the fixture built a candidate from the private approval rows and called the writer on private descriptors. After restart the broker reconciled the approval without double credit, two snapshots showed usage increasing, and the same job finished successfully. The fixture writes only its container-private state. The candidate's `repair_authorized` field remained false throughout.

Separate temporary-file checks covered an already-held witness lock, content change before write, a failed witness append followed by a retry, a torn witness append being refused, an incorrect append flag, and the successful marker write. These are injected software errors, not hardware power-loss or storage durability tests. The writer has no production command and does not independently validate trusted path opening, backup, database consistency, full WAL semantics, service lifecycle or scheduler reconciliation. A partial write can leave an invalid marker requiring further recovery. Do not deploy or use it on production as a complete repair procedure.

After the isolated runs, the host scheduler queue was empty, `slurmctld`, `slurmd` and the backend were active, `/dev/nvidia0` retained `other::---`, and `SlurmctldParameters` was unset. Monthly enforcement remains disabled.
