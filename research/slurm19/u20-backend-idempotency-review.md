# u20 backend submission idempotency candidate

This patch applies to the captured u20 runtime backend SHA-256 `65d213100a0e0ebd3f9fe87b51d1625f8539acf954ca572b43fa48a07c43173c`, not the different repository backend. For jobs with a client request ID, it stores a versioned SHA-256 fingerprint of the canonical request JSON alongside the job in the same SQLite transaction. An identical repeat returns the existing job; a changed request using that ID gets a conflict. Older rows lacking a digest are explicitly unverifiable and must be queried, never silently assumed identical. A consumed temporary authorization cannot be reused with another request ID. Fingerprints are omitted from job API responses.

Exact JSON identity is intentionally conservative: equivalent omitted/default fields are not interchangeable. The runtime currently accepts requests serially in one socket loop; the existing unique index prevents duplicate rows if multiple processes race, but a concurrent conflicting insert may yield a generic error rather than a clean conflict. This patch does not cover other mutation endpoints or prove exactly-once dispatch. Python AST parsing succeeded; no tests or production changes were made. Applying it would migrate the live database and restart the backend, so first review schema compatibility, back up the database with SQLite-aware procedures, protect jobs, verify target hash and satisfy deployment recording.
