# u20 逐任务 GPU 用量：现有证据与实现边界

2026-10-31，检查已提交的 Slurm 19 控制器补丁、控制接口和平台数据库定义，目的是确定能否为 4090 页面提供可信逐任务月用量。

现有控制器的 `PREPARE` 事件包含 Slurm job ID、用户 UID、控制器分配 generation、GPU 数和起始时间；`COMMIT`、`SETTLE`、`RELEASE` 事件关联 job ID 和 generation，记载相关时间。控制器已有按北京时间自然月切分区间的计费逻辑。现有 `SNAP` 接口返回的是 UID 级月汇总和活动分配数量，并没有返回逐任务账目。控制器的离线账本检查工具要求取得独占锁，故不应在运行中的生产账本上用它当在线查询器。

平台 jobs 表保存平台任务 ID、scheduler ID、owner UID 和创建时间，但现有定义没有持久化控制器 generation。仅按 scheduler ID 或用户名连接账本存在编号重用和身份歧义；不能把 `sacct` 的总运行时乘 GPU 数直接声称为控制器已结算的本月用量。WAL 可能包含逐次分配所需事件，这只是源码级发现，还需要对当前部署版本、截断恢复和完整历史做验证，不能直接将正在写入的 WAL 当作可靠查询接口。

可行的后续实现应在控制器的受锁状态中维护或安全投影 `(uid, job_id, generation, month)` 的已结算量，使用与总账同一分月算法、GPU 数和精度；运行中的未结算区间与已结算部分要以同一个快照时间合并，禁止重复计算。上线前需解决平台任务到 generation 的可信绑定，历史编号复用或事件不完整时明确返回不可用；控制器重启、跨月、运行时查询与释放交错、账本恢复失败都必须得到明确行为。接口应由现有 root 认证通道提供，并由 broker 根据登录用户权限过滤；无可靠关联时页面继续显示“暂无任务用量明细”。

此记录是设计调查，不是实现或线上核验。没有读取或修改生产 WAL，没有重启控制器，也没有改变用户账本。

随后新增离线原型 `u20-training-platform/tools/monthly-job-projection.py`，仅接收调用方提供的完整 WAL 字节，按 UID、作业号、分配 generation 和月份投影已结算用量；开放分配作为未完成信息返回，不估算其未结算时间。合成数据检查跨北京时间月界、RELEASE、截断、序号倒退和未知事件拒绝。该原型没有自行校验生产账本来源、checkpoint 完整性、当前控制器补丁兼容性，也没有处理用户身份绑定或实时快照；不得直接接到线上或将其结果作为正式账本，仍需完整审查及覆盖上述场景。

补充对照 `ledger-recovery-fix.patch`、`replay-identity-fix.patch` 和 `grant-idempotency-fix.patch` 后，原型收紧为连续 WAL 序号、递增且非零的分配 generation、非零 GPU 数，并拒绝同一追加 ID 的冲突记录和月累计溢出。合成检查覆盖跨月及六种损坏或身份异常。它仍不能证明与线上运行的二进制完全一致，也不能代替控制器自己的恢复和快照校验。

原型另提供离线 WAL/checkpoint 校验入口；对照后续 `wal-checkpoint-sha256.patch` 发现候选控制器使用的是序号加完整 WAL 摘要，而非早期仅有序号的格式。原型现在要求 SHA-256，合成检查覆盖序号不符、缺结尾、旧格式、摘要不符以及 WAL 内容改变。序号及摘要匹配不能证明文件来自可信控制器、读取时一致或没有被整体回滚；调用方还必须验证独立见证、来源、新鲜度及版本。未部署到 u20。

后续在 u20 的 `time-stock-node:328bec3` 镜像（`sha256:3af9ef9def89ab0334b2ffb9f3a875e3f4fb815acbe18b89ec6da0bcb4c2fb5e`）内，以 `runc`、无网络、容器私有状态及虚拟 GPU 运行 `/opt/time/slurm19-7a06cfff70a7` 候选控制器：账本、checkpoint 和见证均为隔离副本，没有挂载真实 GPU 或生产账本。合成作业被取消并发生 RELEASE 后，原型投影与控制器 SNAP 的已结算汇总均为 4,163,752,770 GPU 纳秒，WAL 序号 3、无开放分配。镜像依赖缺少 `munged`，前两次准备分别因缺少程序、缺少隔离主机名及节点依赖而失败；成功演练以只读方式提供系统 `munged` 和 libmunge，使用容器内置节点进程并设置本地域名。此前活动任务演练也成功读取序号 2、一个开放分配；不把其未结算量算作已完成用量。此单任务、单卡隔离对照不证明真实设备、并发、跨月恢复、独立见证核对或线上身份绑定。

**主机权限异常：**隔离演练后例行检查发现 `/dev/nvidia0`、`/dev/nvidiactl` 和 `/dev/nvidia-uvm` 的 other ACL 均为 `rw-`；检查前最近一次有记录的 `nvidia0` 为 0660。17:05 CST 运行既有 `/usr/local/libexec/pro6000d-gpu-acl` 后，三个节点均恢复 `other::---`，Slurm 两个服务和平台后端 active、队列空。没有证据证明本次无真实 GPU 挂载的演练导致了权限变化，也未确定发生时间或根因；设备权限重建与特权进程路径仍需排查，不能声称持久修复。正常训练用户的会话设备组限制有单独的 SSH/Cockpit 验收证据，但不能以其推断所有访问路径安全。
