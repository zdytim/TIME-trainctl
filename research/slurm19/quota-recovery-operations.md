# Monthly quota recovery: preliminary operator procedure

This procedure is for the staged witness candidate only. It is not authorization to install it or reset quota state. A mismatch or a failed append means that new GPU allocations must remain blocked; already running work must be protected. Do not delete, rewrite or reinitialize the ledger to make a check pass.

1. Record the time, systemd status, controller version and any relevant errors. Identify running, completing and pending work using read-only Slurm commands. Do not cancel or requeue users' jobs. Keep evidence of grants and approvals. The witness and ledger can differ after a crash between fsync operations, so a mismatch does not alone identify the correct contents.
2. Arrange a safe maintenance window and stop the controller only after determining the effects on real workloads. Before doing so, preserve evidence and verify the service and queue state again. This step is not a claim that stopping is harmless; the live release plan must specify what happens to every job and provide a rollback.
   In the isolated Slurm 19 fixture, `scontrol shutdown` also stopped the node daemon and left a finished job in COMPLETING. Do not use that command as a presumed controller-only stop when protecting running jobs. A process signal in an isolated fixture is not by itself a reviewed production stop procedure.
3. Once the controller has stopped and released its locks, create a root-only, restorable copy of the WAL, checkpoint, witness, scheduler state and relevant platform database using methods appropriate for the files. Record paths, ownership, permissions, hashes and timestamps. Do not put state, credentials or backups in Git.
4. Run `sudo python3 time-quota-recovery-inspect.py` using the installed copy reviewed for the candidate. It acquires nonblocking exclusive locks in launcher order, checks ownership and private file modes, reads the three files, reports their sequence numbers and digests, and makes no changes. Exit 0 means those limited checks match; exit 2 means the three disagree; exit 1 means inspection was refused. Any lock failure means the files must not be treated as an offline snapshot.
   The updated offline inspector also compares each witness digest against its corresponding WAL prefix. Previously a modified earlier witness digest was missed if the last digest still matched. This is an offline diagnostic improvement only: it does not establish event semantics or repair state, and the staged controller itself still checks the last witness digest on startup.
   It reports whether the checkpoint digest matches its WAL prefix and labels two structural shapes: `wal_one_event_ahead` and `witness_one_event_behind`. Either can resemble an interruption between the ordered writes, but the shape alone cannot establish its cause, event validity or whether a scheduler side effect occurred. Both remain mismatches with exit status 2; no file is changed and `recovery_readiness` remains `not assessed`.
5. Treat every result, including matching digests, as insufficient to resume by itself. Reconcile WAL events and stored grant IDs against the controller's recovered job state and the platform's durable outbox and approvals. Establish whether an interrupted event was actually applied and whether an allocation was started or completed. The current candidate does not supply a reviewed automated reconciliation or safe repair procedure. Preserve evidence and keep admission closed until a separately reviewed recovery method is available.

`time-grant-recovery-evidence.py` supplies a pure, offline comparison for a complete GRANT event and caller-supplied outbox/application rows. It checks the UUID, target UID, month, integer GPU seconds, original actor UID, approval amount and coherent pending/approved status. A match only establishes that those supplied values agree; it always returns `repair_authorized: false`. It neither acquires a consistent SQLite snapshot nor checks the full ledger, controller job state, event uniqueness or actual persistence. It is not installed on u20 and must not be used alone to rewrite markers or resume scheduling.

`time-grant-repair-candidate.py` builds in-memory marker bytes for the two one-event lag shapes only after that comparison, prefix-digest checks and a duplicate grant-ID scan. It checks the proposed marker bytes against the same structural inspector and always returns `repair_authorized: false`; it performs no file I/O itself. This is not a complete WAL semantic replay, a consistent database snapshot, a safe transactional file replacement, or job reconciliation. It remains research code, not a deployable repair command. No marker may be changed solely because it emits candidates.

The witness is on the same host and its descriptor is writable by the controller. A whole-filesystem rollback, root compromise, controller compromise, or physical storage failure is outside its protection. No claim of hardware power-loss safety follows from matching checksums.

The `dbd004e` inspector and fixture ran in a networkless disposable container on u20 on 2026-10-30. The fixture verified a matching empty ledger, refusal while the witness was locked, a mismatching witness, malformed witness sequence and a witness symlink. It did not replay business semantics, validate a real scheduler state or test power loss. The tool is not installed on the live system.
