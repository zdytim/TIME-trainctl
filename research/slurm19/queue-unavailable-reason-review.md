# Queue reason when monthly ordering is unavailable

The controller stopped a mixed queue if it could not obtain the fresh monthly tier snapshot, but did not update pending GPU jobs' descriptions before stopping. Those descriptions could still say `single-node GPU selection is not provable`, even when the ledger/witness was unavailable. The `758e98a` patch marks pending GPU jobs in the affected queue with `MonthlyGpuQuota:quota state or ordering unavailable` whenever the snapshot or ordering check fails. The scheduling admission checks remain unchanged. CPU-only jobs are not given a GPU quota reason; an unhealthy mixed queue can still be conservatively paused.

Both current callers hold Slurm's job write lock. A copied `0dc0b40` source tree was patched and incrementally compiled on u20; the isolated candidate controller SHA-256 was `5f39676d9de6a536e644df416f5c21db10aa389771486002fa86c4df45b5a903`. In a networkless private-state container with fake GPU and stock u20 node daemon, a rolled-back WAL/checkpoint with newer witness produced an unavailable quota response; the GPU job stayed pending with no node and showed the new reason. The CPU job behind it also stayed pending and the WAL was unchanged. Separately, with a valid ledger and exhausted user, the reason stayed `monthly_capacity_exhausted`, the job did not allocate a node, and the candidate broker's idempotent grant allowed the same job to start and finish. These are synthetic cases, not a live GPU or full fairness test.

The Cockpit queue presentation maps those two scheduler reasons to separate Chinese messages, while retaining unknown reason strings and escaping them. This changes display only; API reason codes are preserved. The controller, UI and broker changes remain staged, and this incremental build is not a production release bundle.
