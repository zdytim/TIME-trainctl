# u20 GPU device recreation risk

Read-only inspection on 2026-10-30 found that `/dev/nvidia0`, `/dev/nvidiactl` and `/dev/nvidia-uvm` currently have `other::---` ACLs and the ACL service is enabled. Both Slurm daemons depend on the oneshot ACL service. The tested current nodes are therefore protected for the previously checked identities; this says nothing about future nodes.

The installed `/etc/udev/rules.d/90-pro6000d-training-gpu.rules` invokes the ACL helper only for `add|change` events whose kernel name matches `nvidia*`. However, `udevadm info -q path -n` returned `Unknown device` for all three current compute/control nodes, and `/sys/dev/char/195:0` and `/sys/dev/char/195:255` were absent. Thus there is no evidence that these manually created device nodes produce the matching events. The installed NVIDIA vendor rule invokes `/sbin/ub-device-create` for the NVIDIA PCI driver and UVM module add events; the utility is an ELF binary from `nvidia-kernel-common-570`. The current driver parameter `DeviceFileMode` is decimal 438 (0666) with `ModifyDeviceFiles: 1`. This is an exposure risk if device nodes are recreated without the ACL service or another effective policy; it is not proof that recreation occurred or that a particular utility uses that parameter.

The oneshot service cannot by itself guarantee protection against later recreation after it has exited. Adding a later udev RUN action to the vendor's module/driver events may improve restoration but does not prove atomic, race-free denial while nodes are being created and does not cover every creator. Before claiming that unprivileged users cannot bypass scheduling across driver reloads or reboots, identify all node creators and establish restrictive creation permissions before access, then verify boot, reload and recreation paths in an isolated or controlled maintenance environment. Do not trigger a driver reload or recreate current devices while existing desktop/GPU work may be using them. No rules, devices, driver settings or services were changed in this inspection.

Subsequently the exact installed `/sbin/ub-device-create` and its PCI library were copied into a networkless, read-only container with a private `/dev`, no passed-through GPU devices, no host mounts, and only MKNOD, CHOWN and FOWNER capabilities. With umask 000, this program created container-local NVIDIA compute/control character nodes at mode 0666. In a separate container, after initial creation the fixture changed its private `/dev/nvidia0` to 0600; rerunning the same program changed it back to 0666. The host's sysfs and `/proc/devices` were read for detection, but no host device node was touched. This demonstrates the observed utility can reopen access on its own execution; it does not by itself establish every production event sequence, actual device accessibility from the container, or a safe automatic fix. Setting `NVreg_DeviceFileMode` alone must not be assumed to control this independently implemented utility. No production udev trigger, device recreation or driver reload was performed.

The live host uses cgroup v1 devices and has `DevicePolicy=closed` for the enrolled `timzhang` user slice. A bounded probe `f4f458b` created a temporary 0666 character node for the same device number under a private root-owned directory on `/dev`; root opened and immediately closed it, while a transient `timzhang` service in `user-1001.slice` received `EPERM`. The probe removed its own node, directory and transient service; it neither changed existing `/dev/nvidia*` nodes nor launched compute. An earlier version placed its node under `/run`, which is mounted `nodev`; its denial was a false positive and is withdrawn. The corrected check supports an additional safeguard for the tested enrolled account and slice, but does not prove coverage for unenrolled accounts, escaped sessions, other device types, or the full reboot/driver-reload lifecycle. It does not remove the recreation risk.

The prior PAM session guard only looked for the user's slice name in any cgroup hierarchy. A user manually added to the training group without the enrollment procedure could therefore enter a correctly named slice without proving that GPU devices were denied. The staged `90fa24a` guard additionally requires the active slice's `DevicePolicy=closed`, membership in that slice in the cgroup v1 devices hierarchy, and a current kernel `devices.list` that grants no access to the observed NVIDIA character devices. Missing data, unrestricted/wildcard matching device rules and malformed rules fail closed. Admin users remain excluded from this training-user check. Synthetic checks cover correct and incorrect slice paths, open policy, wildcard GPU permissions and absent GPU nodes.

On u20, the exact staged guard (SHA-256 `274a70e98183d0055d063c19f4eb24a0569d883788fe2f98bcf2545417a0ecab`) accepted a root-run transient service representing `PAM_USER=timzhang` inside the existing `user-1001.slice` and denied an invocation outside that slice. The check used the real host device hierarchy, but did not replace PAM, perform a real login, test cgroup v2, or test a change of devices or policy after login. The guard is not a complete defense for unenrolled non-training accounts, dynamically appearing GPU device numbers, privileged users or other execution paths; `ub-device-create` can still change device-node permissions. The existing production guard remains in place.

On 2026-10-30 a separate temporary PAM session stack exercised `pam_systemd` followed by `pam_exec` invoking the exact staged guard for `timzhang`, from a bounded transient service. It accepted an open session; a separate stack whose execution module was `/bin/false` refused open, demonstrating that a required session module failure is not ignored. The denied-open fixture's `pam_close_session` returned 6; logind collected the temporary sessions asynchronously, and a bounded comparison confirmed the user's session set returned to its original state. The temporary PAM files were removed, the scheduler and training service were active, the scheduler queue was empty, and Sunshine remained on the GPU. Authentication and a complete SSH or Cockpit login were not tested; the existing PAM service stack was never replaced. Earlier runs using mixed-case temporary service names selected PAM's fallback and are invalid; an intermediate cleanup check also failed until asynchronous collection was observed. None of those runs counts as a passing integration result.
