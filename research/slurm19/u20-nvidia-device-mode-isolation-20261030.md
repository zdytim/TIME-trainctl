# NVIDIA device permission investigation on u20

NVIDIA's x86-64 570-series FAQ documents `NVreg_DeviceFileUID`, `NVreg_DeviceFileGID`, and `NVreg_DeviceFileMode` for device file defaults and `NVreg_ModifyDeviceFiles=0` to disable dynamic modification: https://download.nvidia.com/XFree86/Linux-x86_64/570.144/README/faq.html. The running host reports driver 570.133.07, `ModifyDeviceFiles: 1`, `DeviceFileUID: 0`, `DeviceFileGID: 0`, `DeviceFileMode: 438` (0666). `modinfo -p nvidia` lists those parameters. The exact running version and package-specific boot behavior still need validation.

An isolated networkless container using the normal `runc` runtime, private `/dev`, `CAP_MKNOD`, and narrowly scoped GPU device cgroup rules created its own character nodes for the real GPU. Container device inode `1048639:17` was distinct from host `/dev/nvidia0` inode `5:684`. With a read-only bind of the host `nvidia-smi` and NVML library, the real 4090 query succeeded and the container's private GPU/control/UVM nodes changed from 0600 to 0666 under the host's currently exposed NVIDIA parameters. This confirms the mode behavior for the private nodes; it does not test a different loaded module parameter, persistence over reboot, actual host device recreation, or protection of all device paths. Existing GPU workloads were not stopped.

An attempted private bind mount of a synthetic parameter file over `/proc/driver/nvidia/params` was rejected by the OCI runtime's proc safety policy before the container started. No bypass was attempted and the failed attempt is not evidence for the proposed parameter change. An additional trace fixture could not start because its container lacked a required strace library; it is not counted as a successful trace.

During investigation, host `/dev/nvidia0` was again observed as `other::rw-`. Several preceding container invocations and other concurrent processes make the triggering process unproven. The existing ACL helper was immediately reapplied and a subsequent read showed `other::---`; the queue was empty and Slurm and the backend remained active. The earlier observed `ub-device-create` behavior independently sets nodes to 0666, so a driver mode parameter alone is not sufficient evidence of a race-free policy. No module parameters, initramfs, udev rules, or driver were changed. Monthly enforcement remains disabled.
