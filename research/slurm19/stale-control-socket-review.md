# Isolated crash and quota socket recovery

In a networkless test container, killing the candidate Slurm controller while a fake GPU job was running left the job running across controller restart. The old Unix socket file remained, however, so the restarted controller logged `monthly quota control socket unavailable` and the platform could not query quota or approve grants. This was observed with `67812e7`; the live controller was not touched.

The staged fix permits cleanup only when this controller owns an open, healthy, reconciled and exclusively locked WAL/checkpoint; the existing path is a service-owned private Unix socket; a nonblocking connection fails specifically with `ECONNREFUSED`; and a second `lstat` finds the same device and inode. A live listener, regular file, symlink, wrong owner, unsafe permissions, unavailable ledger, ambiguous connect failure or changed identity is retained and startup reports the socket unavailable. The service-owned, non-group-writable state directory is the trust boundary; a malicious process with the same service UID remains outside that guarantee, including the narrow `lstat`/`unlink` race. This patch must pass isolated abrupt-restart, live-listener and non-socket preservation tests before deployment.

The committed `ae47c8f` patch was applied to a separate candidate source copy and compiled on u20 (controller SHA-256 `87ea98c9c16adb9dab5e098f3f04b6c8d2bbde65a960cccf9f99eea6dafc69d2`; this incremental build retains the `67812e7` prefix and is for isolation only). In a networkless container with no host mounts or GPUs, killing the controller while a fake GPU job ran and restarting it restored the quota socket, the active allocation snapshot and the running job. Separate fixtures preserved a same-name regular file and a live Unix listener with unchanged inode; both caused the controller to report the control socket unavailable. These cases do not prove race freedom, power-loss recovery or live-host compatibility. No production service was restarted or changed.
