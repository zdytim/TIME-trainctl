# Isolated broker approval and grant-marker recovery

On 2026-10-31, committed fixture `d456a97` was run on u20 in two separate networkless containers with private Slurm state, private witness tmpfs and a private SQLite database. Image `time-grant-db-recovery:d456a97` had SHA-256 `f9f6ab9883bcb945f919fb93de1e455c5959c93b48f25515f7991c27e8087582`. Its broker SHA-256 `4224e6aa116532585c6c9e837ee102e9d508ef00b04e6e685bd5e6f092e88821` matched the running u20 broker at the previous deployment, and its controller was the staged `7a06cff` candidate. No production state, user files or GPU devices were mounted.

For each of the `wal_ahead` and `witness_behind` cases, the real broker created a monthly request and an administrator approved it. The real controller accepted 3,600 GPU seconds; an injected lost response left the actual private SQLite outbox `PENDING` and application `GRANT_PENDING`. After clean controller shutdown, the fixture deliberately rewrote private markers to simulate the selected lag. The restarted controller returned quota unavailable. Following another clean stop, the fixture loaded actual rows from its SQLite database, generated candidate markers, and wrote them inside the disposable container. The controller restarted, and the broker retried the same grant ID: the application became `APPROVED`, the outbox became `APPLIED`, and the controller still reported exactly 3,600 GPU seconds, demonstrating no double credit in these cases.

The SQLite schema and broker/controller methods were real, but the data, lost-response injection and marker corruption were synthetic. There were no running or queued jobs and no real crash, torn write, live database snapshot, production marker write, or power failure. This does not establish safe transactional repair or running-job reconciliation. The fixture explicitly observes that candidate generation does not authorize repair; it writes only container-private files. The quota gate remains disabled. After testing, the u20 queue was empty, its Slurm and backend services were active, `/dev/nvidia0` had `other::---`, and `SlurmctldParameters` remained unset.
