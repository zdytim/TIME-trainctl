# u20 isolated GPU queue observations

On 2026-10-30 the corrected `08b076a` controller was run in the dedicated networkless test container with its own Slurm configuration, MUNGE key, state and a regular file representing one fake GPU. No host GPU, live state, host networking or existing service was used. A fresh ledger produced debug tier, but a submitted `--gres=gpu:1` job remained pending with `MonthlyGpuQuota:single-node_GPU_selection_is_not_provable`. The eligible-job expectation failed: this candidate cannot yet be treated as usable.

A synthetic ledger charged 605 GPU-hours to a separate container-only root identity and its quota socket reported tier `exhausted`, zero remaining and 2,178,000 GPU-seconds used. Its fake GPU job remained pending with `NodeList=(null)`, but the reason was also `single-node_GPU_selection_is_not_provable`, not quota exhaustion. An earlier script labelled that result a pass merely because it contained `MonthlyGpuQuota`; that was a false positive and is explicitly withdrawn. The corrected script requires the specific exhausted reason and separately checks that an eligible job starts. Neither this result nor fake resources prove real-device enforcement. The cause of the unavailable selection metadata must be established and repaired before further release consideration; quota enforcement remains disabled on u20.

An isolated diagnostic build showed two separate selection calls: the first had no node or selection arrays, while the subsequent single-node selection had a count array but no bitmap array. Inspection of Slurm 19 `gres.c` shows its `node_specs->topo_cnt == 0` path deliberately fills counts and continues without allocating `gres_bit_select`. The staged `selector-count-only-fix.patch` accepts the selected count without a bitmap when the array is absent, but continues requiring exactly one selected node, the per-node request, the selected count and the aggregate to agree. If a bitmap is supplied, its cardinality is still checked; after allocation, the existing code still requires and checks the allocation bitmap and fails closed on mismatch. This may still deny unsupported device layouts or fail after allocation; tests must determine actual behavior. No diagnostic build is eligible for deployment.

The committed `42470c6` candidate rebuilt with SHA-256 `d4dd849ec999cdb4b32a132c18dc9d077f4d3dd5ddafd0ce63711f0e906584ff`. In the same isolated one-node fake-GPU setup, the exhausted user's job remained `PENDING` for `MonthlyGpuQuota:monthly_capacity_exhausted` with `NodeList=(null)`. A fresh eligible user received the node and, after the fixture's `/tmp` was explicitly mounted executable, the fake GPU job reached `RUNNING`. A live controller snapshot reported one active allocation, one GPU and more than two GPU-seconds of accrued usage. The prior eligible run reached allocation but exited with code 2 because Docker's default tmpfs mount was `noexec`; `slurmstepd` reported permission denied. That fixture failure was not counted as a controller pass. The successful fixture remained networkless, without host mounts or GPUs, with bounded resources and a read-only image; only its private tmpfs allowed execution.

These observations cover one fake GPU, one local node and a short run. They do not prove real GPU device isolation, full multi-GPU accounting, all tier transitions, month crossing, restart/recovery, backfill races or compatibility with the production plugin set. Production remains unchanged and the monthly gate remains disabled.

Further isolated runs using the same `42470c6` controller established that a four-fake-GPU job reached RUNNING and the difference between two projected usage snapshots was exactly four times the corresponding elapsed snapshot time. Synthetic ledger cases also returned tier 0 immediately below 5 GPU-hours, tier 1 at 5, tier 2 at 105, and tier 3 at 605 GPU-hours. In a separate four-fake-GPU run with four GPU-seconds left, a one-GPU job continued RUNNING after capacity was exhausted; the controller reported positive overage, and a second one-GPU job stayed PENDING with `monthly_capacity_exhausted` and no node allocation. A first attempt at this case hit the fixture's 8-second controller timeout; a second left insufficient simulated memory and produced `Resources`, so neither was counted as a pass. The final run used a 45-second test timeout and spare simulated CPUs/memory.

The later incremental `ae47c8f` candidate was also exercised with three container-only user accounts and one fake GPU. After a separate blocker occupied the GPU, normal, important and debug jobs were submitted in that order. Once the blocker was cancelled inside the fixture, their observed start markers were `debug`, `important`, `normal`. This is a single-node, no-reservation ordering case, not proof of all preemption, partition or backfill combinations; the third task had started when the fixture ended.

An additional fake-GPU case configured a typed `gpu:fixture:1` resource and submitted the corresponding request. The `ae47c8f` candidate kept it PENDING with no node allocation and an explicit unsupported typed/duplicate/GPU-like GRES reason. This confirms refusal for that tested typed shape; it does not cover MPS, MIG, shard, arbitrary aliases, or actual NVIDIA device enforcement.

These are point-in-time synthetic cases, not proof of all backfill paths, cross-month accounting, crash durability, grants, real NVIDIA devices, or production ABI compatibility. The isolated job was terminated with its container; no production job or service was modified.

With the later `67812e7` candidate, the exhausted one-GPU case and the eligible four-GPU multiplier case were repeated successfully. A one-GPU synthetic job started with four GPU-seconds remaining, continued past exhaustion, finished with exit code 0, and was removed from the active-allocation snapshot while its overage remained recorded; a second job stayed pending without node allocation. A separate running fake-GPU job and its active accounting survived a clean isolated controller shutdown/restart. These are clean restart and short fake-workload observations, not power-failure or real-GPU evidence.

With the checkpoint missing or WAL truncated, the isolated quota socket returned `ERROR unavailable_or_invalid` and a fake GPU job stayed pending with no node for the observation period. Its reason remained the earlier `single-node_GPU_selection_is_not_provable`; therefore the specific ledger-failure reason was not demonstrated. A separate missing-checkpoint run with only a CPU job also left that job pending with `Reason=None` for ten seconds; this is not caused by competition with the preceding GPU job. Source inspection indicates queue freshness requests a ledger tier snapshot for every user and stops the scheduling pass when that snapshot is unavailable, including a CPU-only queue. Treat this as a degraded-service behavior requiring a deliberate policy decision or correction, not as evidence that unaffected CPU jobs keep running. No real services were changed.

The healthy-ledger control case using the same isolated CPU-only fixture reached RUNNING, confirming the node could execute it. The staged `cpu-only-queue-failure-fix.patch` skips GPU-tier freshness only when the current job and every remaining queued job have no GRES records at all. It deliberately retains the fail-closed behavior for mixed queues and any other GRES; it does not assert that CPU-only jobs behind GPU jobs continue during ledger failure. The patch requires rebuilding and re-running both healthy and damaged-ledger cases before it is considered valid.

The `67812e7` build (controller SHA-256 `9ab310a02c46ab64dfa11c3c08424e326b80cb02cc150573356512de36c5d22f`) subsequently ran the missing-checkpoint CPU-only fixture successfully: the quota socket remained unavailable, while the single CPU job reached RUNNING. The healthy CPU control passed on the previous candidate, and GPU exhaustion/four-GPU cases passed again on `67812e7`. The build connection ended unexpectedly after the build log reached the end of `make`; wrapper exit status was not observed, so the resulting files were independently inspected and exercised rather than asserting the complete build command succeeded. Mixed queues and additional GRES remain conservative and unverified.

On the `67812e7` isolated fixture, both missing-checkpoint and truncated-WAL cases returned a quota error, retained the exact WAL hash, and left the fake GPU job without a node allocation over the observed interval. With both GPU and CPU jobs queued, both remained pending: this confirms the intentional conservative mixed-queue limitation. The GPU job's displayed reason was the earlier selector message, so the fixture does not establish accurate diagnostics or every scheduling path. No production state was used.

An isolated grant run added 20 GPU-seconds against 40 seconds of overage, repeated the same ID without duplication, rejected a conflicting same-ID request, then added another 40 seconds; the remaining quota was 20 seconds. The same grant and usage values were observed after a clean isolated controller restart. This does not establish behavior during power loss or a concurrent live restart.

On 2026-10-31 at approximately 17:20 CST the later `7a06cff` controller was exercised in `time-stock-node:328bec3` (`sha256:3af9ef9def89ab0334b2ffb9f3a875e3f4fb815acbe18b89ec6da0bcb4c2fb5e`). This run used `runc`, no network, private controller state and witness, four synthetic GPUs, a stock node daemon, and no NVIDIA device mounts. An isolated root-owned synthetic account began with four GPU-seconds remaining. Its one-GPU job continued after exhaustion while the snapshot recorded positive overage. A second one-GPU job remained `PENDING` with `NodeList=(null)` and reason `MonthlyGpuQuota:monthly_capacity_exhausted`, despite spare synthetic GPU capacity. The first job completed with exit code 0; the second remained unallocated, and the final snapshot reported approximately 26.057 GPU-seconds of overage. This is an isolated synthetic-account test, not a production quota exhaustion or a test of every entry point and recovery case. Afterward the production Slurm and broker services were active, the production queue was empty, and the three main NVIDIA device nodes remained `other::---`.

At approximately 17:22–17:23 CST the same isolated image and `7a06cff` candidate were run twice with one synthetic GPU and a running synthetic task. A clean controller stop/restart retained the RUNNING job and returned an increased usage snapshot after restart. In a separate container, the controller child was terminated with SIGKILL; after restart the stale control socket was recovered, the job still reported RUNNING, and accounting was readable. Each used private WAL, checkpoint and witness, no real GPU or host scheduler state. The abrupt-restart case kills a process in a particular fixture state; it is not a physical power-loss test or exhaustive fsync-boundary coverage. Afterward the production services were active, queue empty, and three host GPU nodes remained `other::---`.

At approximately 17:24 CST the same isolated controller was started with a synthetic WAL whose content had been altered after its checkpoint and witness were created. The quota socket returned `ERROR unavailable_or_invalid`; a new GPU job remained `PENDING` with no node and `MonthlyGpuQuota:quota_state_or_ordering_unavailable`. The fixture confirmed the damaged WAL hash was unchanged. A later CPU-only job also remained pending with `Priority` in this mixed queue; this is a real availability limitation in the observed scenario, not proof that all CPU-only tasks are blocked in every configuration. Production services and queue were unaffected and main GPU node ACLs remained restricted. This one altered-content case does not establish behavior for every disk failure or corruption pattern.

At approximately 17:26 CST the same `7a06cff` controller and image ran a separate one-synthetic-GPU grant fixture, using an unprivileged synthetic user UID 1001, isolated broker state and a `slurm`-owned controller. An exhausted user's job stayed PENDING with no node; the fixture exercised a lost grant reply and idempotent broker retry, then the job started and the user command completed. Private checkpoint and witness were enabled; there were no real GPU device mounts or production grants. The production Slurm and broker remained active, its queue empty, and main GPU ACLs restricted. This does not replace an actual production administrator approval or establish all concurrent grant and crash-window cases.

On 2026-10-30 the clean `ae47c8f` release-layout controller was also exercised in the isolated fixture with `SlurmUser=slurm`, UID 64030, matching the u20 service account. An eligible one-fake-GPU job reached RUNNING and accrued usage. In a separate run the controller was killed while a fake-GPU job ran; restarting it recovered the quota socket, the running job and its active accounting. These runs used synthetic devices and container-private state; they do not establish compatibility with the production plugins, actual GPU enforcement or power-loss durability. The monthly quota gate has not been deployed.

The `f8e4c6b` source-level fixture extracted the actual calendar and interval-charging functions from the clean `ae47c8f` source used for the u20 candidate build. On both the Mac and u20, it passed calendar boundary cases from 1970 through 2100, a four-GPU interval spanning a Shanghai month boundary with fractional seconds, and an interval spanning October, all of November and part of December. The computed charge was split between the correct months, with GPU count applied to each segment; a reverse interval was rejected. This calls extracted source functions in a temporary library, not a running controller over a real month boundary, and does not establish controller recovery or scheduler behavior at that boundary.
