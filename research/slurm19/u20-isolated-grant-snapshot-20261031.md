# Offline grant preview with isolated running-job recovery

On 2026-10-31, image `time-grant-snapshot:defab05` (SHA-256 `ab742144ecf7553ae3fd8be6d371ae512348159bd40dbf97bbca47bf5a4c6c25`) ran the `defab05` fixture on u20 in separate networkless containers for `wal_ahead` and `witness_behind`. Each used private Slurm state, witness tmpfs and a real private broker SQLite database, with a synthetic GPU and a running 25-second job. No production database, state directory, user files or GPU devices were mounted.

After a simulated lost grant response, controller SIGKILL and deliberate private marker lag, the fixture stopped the isolated controller without stopping its node daemon. The new preview acquired marker locks, created a private SQLite backup and marker copies, matched the grant against rows from the copied database, and saved candidate marker bytes inside the private backup. The fixture verified those bytes against its independently generated candidate, then used the separately staged locked writer on private marker descriptors. In both cases the controller restarted, the broker completed its idempotent approval reconciliation without doubling the 3,600 GPU seconds, two snapshots showed running usage increasing, and the job finished.

The preview's production `systemctl` check was replaced inside the container by a test callback that inspected the private PID namespace for an active controller; it is not evidence that production systemd lifecycle races are solved. Local temporary-file tests covered active-service refusal, a held witness lock, mismatched grant evidence, a symlink database, changed marker detection, and a successful private snapshot. The preview does not authorize a marker write. No real crash, hardware power loss, full WAL semantic verification or production database mutation occurred.

After the runs the host queue was empty, controller, node daemon and backend were active, `/dev/nvidia0` retained `other::---`, and `SlurmctldParameters` was unset. Monthly enforcement remains disabled.
