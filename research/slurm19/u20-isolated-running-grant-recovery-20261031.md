# Running-job recovery with an interrupted grant, isolated u20 fixture

On 2026-10-31, image `time-running-grant:ead174c` (SHA-256 `7c6d051dc11e921bd857505fe9181ba88608902d27072fa4c6acc59d80087698`) ran the committed fixtures in two separate networkless disposable containers with a synthetic GPU, private Slurm state, private witness tmpfs and private broker SQLite. It used the staged `7a06cff` controller, stock u20 node daemon and the deployed candidate broker; no host device, production scheduler state or user files were mounted.

Each case started a 25-second synthetic-GPU Slurm job as UID 1001, recorded an approved one-hour GPU grant in the controller and deliberately lost its response to leave a real SQLite outbox pending. The test killed only the isolated controller with SIGKILL, then emulated either WAL ahead of both markers or witness one event behind. The restarted unhealthy controller preserved its stale socket and quota requests were unavailable. The isolated controller was then stopped without stopping the node daemon; candidate marker bytes were generated from the private SQLite rows and applied only to the private fixture files. After restart, the broker reconciled the grant without doubling it, the allocation remained running, two quota snapshots two seconds apart showed increasing usage, and the job printed its finish marker and reached COMPLETED.

An initial setup used `scontrol shutdown` during a running job. In this isolated environment that also stopped the node daemon: the job's command printed its finish marker, but Slurm remained in COMPLETING. That run did not pass. The fixture was corrected to signal only the isolated controller and verify the node daemon survived. This observation is a reason not to assume `scontrol shutdown` protects live jobs. Earlier attempts also encountered a preserved stale socket and a test assumption that the grant was the last WAL event; both fixture assumptions were corrected before the successful runs.

These tests manufacture well-formed marker lag after a process kill, not a power loss or torn write. The candidate file writes are fixture-only and are not a reviewed production recovery tool. The tests use fake GPU resources and one short job; they do not establish real-device isolation, every interrupted ledger event, multi-GPU behavior, durable transactional recovery, or safe production maintenance. After testing, the u20 host queue was empty, its controller, node daemon and training backend were active, `/dev/nvidia0` showed `other::---`, and `SlurmctldParameters` remained unset. Monthly quota enforcement remains disabled.
