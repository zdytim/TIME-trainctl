# Staged u20 release-layout build mode

The normal candidate builder deliberately embeds isolated directories. The new explicit `--layout u20-release-candidate --build` mode instead configures a versioned `/opt/time/slurm19-<project-commit-prefix>` runtime prefix, `/etc/slurm-llnl` as the configuration directory and `/var` as local state. The build output remains under the caller's new user-owned output directory; the script does not install, create or alter the embedded system paths and does not execute the resulting controller.

This mode is preparation only. Because the candidate embeds a live configuration path, never run it against production as a validation shortcut. A release still needs a root-owned bundle, explicit library and plugin resolution, package compatibility, a protected maintenance procedure and exact rollback. No release layout is proof of these properties, nor of quota behavior or readiness. The default isolated layout remains unchanged for any authorized container validation.

The committed `393d106` candidate built on u20 in `/home/u20/.local/share/time/builds/release-layout-393d106`. The controller ELF SHA-256 is `197f4ba71d34509d666cfd5b9d99a2120a884ee4bf280585683bd34671ed0560`. Static inspection showed RUNPATH `/opt/time/slurm19-393d10615ee6/lib/slurm`, and the candidate library contained `/etc/slurm-llnl/slurm.conf`; the prospective `/opt/time` release path was not created. Existing Slurm and training services reported active afterward. No candidate, test or workload was run and nothing was installed. A later source revision has a different versioned path and must be rebuilt for that exact revision.

On a subsequent read-only inspection, u20 still reported `SchedulerType=sched/backfill`, `SelectType=select/cons_tres`, `AuthType=auth/munge`, `TaskPlugin=task/cgroup`, `ProctrackType=proctrack/cgroup` and `GresTypes=gpu`. The matching candidate backfill plugin refers to `monthly_quota_queue_current`, which the matching candidate controller exports. Its ELF lists libc and pthread, while the controller depends on `libslurmfull.so` and retains the versioned RUNPATH. The existing system backfill plugin is a separate root-owned file. Consequently, selecting only the new controller while retaining the existing system PluginDir would not load the matching candidate backfill logic. A safe release needs an explicitly reviewed plugin directory containing all required compatible plugins and consistent resolution for controller and other Slurm processes; symbol presence does not establish ABI or behavioral compatibility. At inspection Slurm and training services were active, `squeue` returned no entries, and `/home` had approximately 25 GiB free (94% used). These are point-in-time observations.

Further static inventory found the candidate did not build `auth_munge.so`, `cred_munge.so`, or `job_submit_lua.so`. The live configuration explicitly requires `auth/munge` and `JobSubmitPlugins=lua`; its installed Lua plugin needs `liblua5.1.so.0`, and its authentication plugin needs `libmunge.so.2`. The candidate configure log reports both Lua and MUNGE development dependencies unavailable; package metadata showed `libmunge-dev` and `liblua5.1-0-dev` as not installed. No package was installed. The existing candidate is therefore not a complete release bundle. The builder now refuses to report success for a u20 release-layout build when the explicitly listed required plugins are missing. That check is a minimum inventory safeguard, not evidence that every needed plugin or library is present, compatible, or safe to load. A future build must identify and pin compatible build dependencies and retain the live security policy; copying existing plugins into a new tree without ABI review is not sufficient.
