01 · 先给决定

A

为什么不把 SPANK 当门

SPANK/prolog/epilog 位于执行或节点侧，适合启动后最后一道保护或清理记录，太晚才知道 Slurm 已分配了资源。它不能满足“尚未运行的作业不分配 GPU”，也不能代替控制器内的并发线性化。

B

为什么保留现有 GRES/cgroup

Slurm 已有的 GRES 计数与 cgroup 设备约束是资源/隔离边界，不是额度 authority。除非实际源码审计发现无法取得 allocated GPU TRES，否则不应为了月度门控重写它们。

05 · 19.05.5 调用链

最有价值的插点在资源提交前，但它不是现成的原子点

源码审阅给出了一个很小的公共覆盖面：直接资源申请最终走 job_allocate → _select_nodes_parts → select_nodes；主调度和 backfill 也直接调用 select_nodes。因此 gate 应在控制器公共路径，而不是只在平台 API 或节点侧。

源码支持的事实

  • node_scheduler.c:select_nodes 先做 pre-select，再由 _get_req_features 得到候选资源；随后按候选节点数构造 TRES 计数。
  • 该函数在约 post-select 位置调用现有 acct_policy_job_runnable_post_select；之后才执行 _preempt_jobs，再进入 bb_g_job_begin、select_g_job_begin、JOB_RUNNING、allocate_nodes。
  • test_only 在实际资源提交前返回；因此任何月度账本写入都必须排除 test-only。

源码尚未支持的证明

  • 候选选择结果、账本 durable commit、GRES 变更和节点 allocation 不是一个现成的 ACID 事务。
  • select/cons_tres 内调用 gres_plugin_job_alloc 会改变资源状态；该调用的错误并不自动变成跨账本回滚。
  • 所以“在 post-select 做一次检查”是好插点，但单独它不是 no-overquota-start 的证明。

对应源码：node_scheduler.c、job_mgr.c、job_scheduler.c、backfill.c、select_cons_tres.c。

07 · 推荐实施

分阶段做一个小的控制器补丁，而不是第二套调度器

推荐方案的“最小”版本保留 Slurm 的节点选择与设备隔离，仅新增一个版本绑定的 controller 模块和生命周期调用。任何阶段都默认关闭；阶段完成不等于可以上线。

阶段 0 · 现场基线与契约

先确认 u20 真正运行的是什么

只读取得精确 Slurm 版本/构建、SelectType、SchedulerType、AccountingStorage、GRES/cgroup 版本、state save 位置、插件加载顺序、主备形态和现有运行作业；定稿水位语义、admin 规则、typed GPU 规则。

涉及：配置清单、slurmctld -V 输出、源码/ABI 对应关系。当前未做现场变更。

阶段 1 · 可重放账本

整数单位 + 幂等事件 + 同步 WAL

新增 src/slurmctld/monthly_quota.[ch]，并在 src/slurmctld/Makefile.am 纳入构建。记录 cluster、uid、month、job id、allocation generation、GPU 数、墙钟锚点、intent/commit/release、grant 与序列号；用 GPU-seconds 或更细整数，不用浮点。

账本必须在资源副作用前 durable；已有周期 state save 只能做快照，不能替代 admission WAL。默认开关为 false。

阶段 2 · 公共最终准入

在 post-select、preemption 前建立事务

在 node_scheduler.c:select_nodes 中保留 pre-select 的纯读检查；候选 bitmap 和计划 GPU TRES 已知后，执行 prepare（持久 intent/hold），失败返回 accounting-policy pending。必须先在该版本源码中证明计划值与最终 tres_alloc_cnt 一致；否则要增加窄的 pre-commit select 回调。确认没有副作用后，才允许进入 bb_g_job_begin、select_g_job_begin、allocate_nodes；成功后将 intent 转 active。

不得把 permit 带过 backfill 的 lock yield；每次真实启动都最终 recheck。若 select/GRES 部分失败无法回滚，进入 AMBIGUOUS，宁可挡新 allocation。

阶段 3 · 生命周期完整性

让计费区间跟着 ownership，而不是跟着 UI 状态

在 job_mgr.c 的所有 deallocate_nodes 调用、job_epilog_complete、batch_requeue_fini、失败节点处理、suspend/resume 和 select_g_job_resized 周围关闭/开启 generation；在 resize 增量提交前再次准入。

结算使用实际 tres_alloc_cnt；COMPLETING 仍占用就继续计费。没有可靠结束点时不能提前释放额度。

阶段 4 · 调度顺序

单独解决优先级，不把水位塞进 priority 位

在 job_scheduler.c 与 backfill 中刷新可运行性和 pending reason；月界/追加后使旧 queue 失效。不要把 tier 直接 OR 进 job_ptr->priority，也不要假定现有 PriorityWeightQOS 能表达水位转移。初版不因额度触发抢占。

若需要“debug/important/normal”作为排队优先级，先定义可信字段和与既有 fairshare/nice/reservation 的排序关系。

阶段 5 · 恢复、追加与管理

先关门恢复，再开放新 allocation

在 controller.c 完成 job/assoc state load 后、调度/RPC 线程开放前 replay WAL 并核对活动 job；在 state_save.c 触发快照但不把异步保存当提交。追加额度采用管理员认证、月份绑定、幂等键和审计事件；平台 API 只投影/请求，不成为准入 authority。

如果主备没有同一 durable journal，启动后保持 RECOVERING；已有作业继续，新的作业保持 pending。

阶段 6 · 另行批准的启用

只在实际验证通过后切换默认开关

编译、静态检查、配置语法/插件加载、隔离 staging 并发与故障验证、恢复演练、观测和回滚方案全部完成后，才由变更流程决定是否启用。当前交付不包含修改配置、重启、部署或上线。

08 · 证明边界

“GPU 分配前禁止越额开始”目前只能写成待证明性质

判定

当前：NOT PROVEN。 仅有 Python/sacct/Lua、仅有 stock QoS、或在 select_nodes 前做一次余额检查，都不能推出该性质。并发调度、backfill 重新取锁、GRES/节点资源提交、进程崩溃和恢复都会留下竞态窗口。

要取得可辩护的证明，至少需要

  1. 所有真正开始 GPU allocation 的入口都经过同一版本的 gate；test-only 不写账。
  2. 在任何会改变全局资源状态的调用前，按固定锁序持久化 intent，并把 intent 计入并发余额。
  3. 准入使用最终实际 TRES，或使用已被源码证明与最终 tres_alloc_cnt 必然相等的 pre-commit 计算；不能只用用户请求或 walltime 估计。
  4. 资源提交成功/失败/结果不明有明确的 commit、abort、ambiguous 三态；不能把异常当成功或当释放。
  5. 重启能从 durable journal 与 Slurm active job state 重建同一事实；不能只依赖 sacct 的最终记录。
  6. 数组、pack、heterogeneous、resize、requeue、suspend、预留和管理员 override 的行为已覆盖，或明确 fail closed。

目前不能写成“已解决”的句子

  • “现有 TIME gate 已防止普通用户绕过”——它仍是提交层防御。
  • “现有 cgroup/GRES 已证明 GPU 被物理清理/重置”——它们证明的是逻辑资源与设备可见性边界。
  • “账本写入后就不会超发”——若资源提交失败/崩溃时没有两阶段结果，仍可能漂移。
  • “主调度通过就覆盖 backfill”——backfill 有自己的 test/start、锁 yield 和 pack/array 分支。
09 · 物理清理问题

本额度需求不依赖“物理 GPU 清理/重置证明”

直接回答

按目前给出的业务契约，必须证明的是谁在什么时候拥有多少 GPU，以及新 allocation 是否在额度边界前被准入；没有要求证明驱动器、显存、进程 FD 或硬件上下文已被清零。因此不应把“物理 reset 证明”偷偷升级为本项目的必要安全条件。

现有机制能支持什么

  • GRES/cons_tres 记录逻辑 GPU 资源；gres.conf 与 task/cgroup 可限制作业看到的设备。
  • 控制器可以在逻辑 allocation 结束时关闭 GPU·小时区间；如果释放状态未知，可以保守阻止后续新 allocation。
  • 这些足以支持本额度 gate 的资源计量边界，但不等于硬件清洗或内存保密证明。

什么时候才需要另立安全项目

  • 如果威胁模型要求防止恶意用户读取前一作业残留显存/上下文。
  • 如果平台必须证明 cgroup、设备节点、PID/FD、驱动上下文在释放后全部清理。
  • 那是节点侧隔离、驱动能力和证据采集项目；本报告不声称历史原型已解决，也不把它作为月度配额启用前的无依据门槛。

官方说明可参见 GRES、gres.conf 与 cgroup 文档；它们描述资源/设备控制，不提供本项目所需的月度账本或物理 reset attestation。

10 · 高风险故障关闭

故障时只关闭“新分配”，不影响正在运行的作业

这是最符合用户优先级的恢复原则：不为了修复账本而主动杀作业；当事实不完整时牺牲新作业的可用性，直到可重放和对账完成。

状态/触发允许的动作禁止的动作恢复条件
OFF
默认关闭		Slurm 按原行为运行；账本模块只可读取或不加载。不能暗中改变已有调度语义。显式变更、完整验证、另行批准。
RECOVERING
启动/主备切换		保留并观察已运行作业；新 GPU allocation 返回 pending。不能依据不完整快照扣款或取消运行作业。WAL 序列连续、活动 generation 与 job state/GRES 对账完成。
AMBIGUOUS
intent 有、结果不明		把相关 job/用户/月标成未知并保守计入；阻止新的 allocation。不能假设“没启动”而释放 hold，也不能直接重放资源提交。从控制器状态、节点状态和人工审计得到唯一结果；以幂等事件收敛。
DEGRADED
fsync/存储/时钟/锁错误		现有作业继续；新作业保持 pending，并给出可诊断 reason。不能回退到 sacct 轮询或平台 API 放行。存储可写、时钟锚点有效、journal 校验通过后重新 reconcile。
UNKNOWN RELEASE
epilog/节点失败		继续计费至可靠的逻辑 ownership 结束；必要时形成 debt。不能把 epilog 返回或节点 idle 直接宣称为物理 reset 证明。拿到可验证的 Slurm 资源释放事实；否则由管理员按审计事件解决。
锁与 I/O 的取舍：为保证“不超发”而同步 durable 写入会增加 slurmctld 调度延迟；把 I/O 异步化又会破坏线性化。推荐先用单控制器、短事件、固定大小/可校验 WAL 做明确的同步边界，测量后再优化；不要把网络 HTTP、sacct 或平台数据库调用塞进控制器锁内。
