# Real RTX 4090 with isolated quota controller

On 2026-10-30 at approximately 22:00 Asia/Shanghai, the `88d5417` fixture was run on u20 with the real RTX 4090 exposed to a networkless, disposable container through the NVIDIA container runtime. Before launch, the host Slurm queue was empty and `/usr/bin/sunshine` was the only reported GPU compute process. The container had private Slurm configuration, state, database and witness; no host Slurm directories or user data were mounted. It used the packaged `7a06cff` candidate controller (SHA-256 `147017cb8d9f16e92eb8c9d1058f5d13f5abbd8f0da06888c4347be0263f3632`), the u20 stock node daemon and the real controller/broker grant code. The user inside the container was UID 1001, not the host account's production login.

The fixture seeded an exhausted monthly balance and submitted one GPU job. The job remained pending with `monthly_capacity_exhausted` and `NodeList=(null)`. The controller accepted a grant after the fixture exercised lost-response idempotency. The same job then started as UID 1001 with `CUDA_VISIBLE_DEVICES=0`, found exactly one NVIDIA RTX 4090 through the CUDA driver API, allocated 1 MiB of device memory, filled it, read back and checked its contents, freed it and completed successfully. This is a bounded device-memory round trip, not a model-training workload. The short job's Slurm fixture reported successful completion.

Afterward, the host Slurm controller, node daemon and training service were active; the host queue was empty, and the same Sunshine PID was still reported using 384 MiB. The live controller still had `SlurmctldParameters=(null)`; no host service was restarted or configuration changed. `--rm` removed the test container.

The fixture uses `task/none` and NVIDIA runtime device injection. Its container-local NVIDIA device nodes were mode 0666, so it does **not** demonstrate production cgroup isolation, prevention of direct GPU access outside the scheduler, power-loss recovery, real Cockpit authentication, or that the live monthly gate is enabled. The single-GPU result does not prove multi-GPU allocation or accounting. The test's queue preflight is a point-in-time check, not an exclusive host reservation.
