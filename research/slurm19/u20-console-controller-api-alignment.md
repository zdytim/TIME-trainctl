# u20 controller, console and client contract

The earlier runtime-targeted broker returned an `observed` controller snapshot, while the staged Cockpit page expected normalized monthly tiers, an ISO month string and separate enforcement status. The page sent its month string to a broker endpoint requiring an integer `YYYYMM`. Administrators also lacked per-account monthly views in that broker response. Consequently a controller-only cutover would not have delivered the requested usable approval flow.

The staged `controller_view.py` converts a validated controller snapshot into the console's `debug`/`important`/`normal` waterfall, remaining, granted and overage fields, retaining the prior raw snapshot for API compatibility. It rejects inconsistent totals and tiers. The UI converts the displayed `YYYY-MM` back to the integer required by the request API. Admin state includes per-account views; ordinary users receive only their own. Each account view currently performs a controller socket request, so the latency and bounded pagination behavior for large numbers of users still require design before scaling beyond this small deployment.

The candidate reports enforcement ready only if a root-controlled `activation_verified` flag is explicitly true **and** a validated live controller snapshot is returned. Missing configuration, unavailable sockets or invalid data remain staged/unknown; a new grant request and new approval are refused unless grant service is enabled and that verified controller view is available. An existing idempotent application can still be retrieved during an outage; already-written grant intents retain their reconciliation path. The flag is not a substitute for the real cutover review, and it has not been set on u20. CLI and MCP capability discovery now distinguish a server's `enforcing` response from staged or unknown while keeping client support separate.

On 2026-10-30, the `9566337` broker (SHA-256 `7372e1d9ad73f6899aa3f2e79e24aae594e42717ba941a6044ddfb31831ea55c`) and controller package `7a06cff` ran with private SQLite and a private root-owned witness in networkless u20 containers. The real broker/controller calls verified normal user and admin views, the numeric-month application, approval and credited hours, staged and disconnected states, refusal of a new unverified request, and retrieval of an existing idempotent request. Separate runs verified loss-of-reply reconciliation across processes, socket peer identity, ordinary-user approval denial, CLI application and administrator approval. The `b668375` run also exercised MCP's real `time_capabilities` tool over the broker socket. GPU sampling and host metrics were stubbed in the console-view fixture; these runs did not render Cockpit, test production data or activate the live controller. An earlier socket fixture run lacked its CLI files and was not a full pass; it was rerun with the committed client.
