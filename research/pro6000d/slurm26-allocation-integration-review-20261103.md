# Slurm 26 draft: allocation integration review

Reviewed the repacked disabled draft in `slurm26-reservation-draft.patch` against the verified Slurm 26.05.5 source. This is a static review, not an implementation or operational validation. Do not enable or deploy the candidate.

## Blocking findings

1. **No successful GPU allocation path.** In `src/slurmctld/node_scheduler.c` `select_nodes`, the guarded preselection path calls `monthly_quota_intent_prepare`, immediately aborts any successful intent, and returns `ESLURM_ACCOUNTING_POLICY` before `_get_req_features`. Thus enabling the guard makes the classified GPU jobs wait indefinitely; `monthly_quota_intent_commit` has no caller in the candidate source. The abort is a deliberate barrier, not a place to insert a commit without accounting for the selector's side effects and failure paths.
2. **No connected recovery or control service.** `monthly_quota_reconcile`, `monthly_quota_control_start`, `monthly_quota_control_stop`, and `monthly_quota_fini` are defined but have no controller call sites in this source tree. The sole startup hook is a separately guarded read-only audit. `_ensure_module_locked` can be reached lazily, but sets `mq_reconciled = false`, and the preselect path requires a healthy reconciled ledger. Consequently enabling macros is insufficient to provide a usable authenticated reservation and recovery path.
3. **No proven completed-job release.** The only scheduler release hook calls `monthly_quota_release_unproven` immediately after `select_g_job_fini` and before `epilog_slurmctld` and node cleanup; it marks an active ledger unhealthy rather than settling and releasing it. `monthly_quota_release` has no caller. The actual end-of-resource lifecycle and failure outcomes must be established before any refund or reuse is allowed.
4. **Restricted job shapes affect availability.** The guarded `_monthly_preselect_classify` rejects whole-node, array, heterogeneous and other shapes, and rejects ambiguous classification before knowing whether a job is GPU-only. If enabled as written, it can hold CPU work as well as GPU work. Any supported subset and effect on the existing workload must be explicitly established before rollout.
5. **Any running allocation blocks another reservation.** `_reserve1_available` returns failure whenever `mq_active` is nonempty, including when a different user has a committed running allocation. Both live `monthly_quota_commit` and replay of `COMMIT4` also reject the presence of any other allocation. The candidate therefore cannot provide the requested concurrent multi-user operation. Removing either condition alone would be unsafe: committed usage, outstanding reservations, and the shared accounting timeline must first be handled atomically in both live state and WAL replay.

These findings are separate from the broker defects in `broker-reservation-review-20261103.md`. They cannot be resolved by enabling Slurm's native `safe` option or by treating a successful build as proof of the user-requested pre-allocation guarantee. Running jobs must remain untouched; the production UI continues to identify monthly quota as disabled.

`slurm26-reservation-owner-scope-draft.patch` is a narrowly scoped disabled-source follow-up: a prior-month pending reservation for one user no longer blocks the balance check for every other user. Prior-month reservations for the same user still fail closed. It applies with `git apply --unidiff-zero` after the abort and recovery draft patches. This does **not** remove the global active-allocation restriction described in finding 5 or implement concurrent operation. Only static review and reverse patch applicability were performed; no tests or deployment occurred.

`slurm26-other-user-reservation-draft.patch`, applied after the owner-scope draft, allows a user to reserve against their own tier while a different user's committed job is active. An unresolved allocation intent or the same user's running job still blocks the reservation. The separate selector and COMMIT4 restrictions continue to prevent a second GPU job from starting, so this is not a concurrent scheduling implementation or a deployable feature. Reviewed statically; no tests or deployment occurred.

`slurm26-concurrent-commit-draft.patch` adds a separately guarded experimental `COMMIT5` ledger writer and replay handler. Its intended transition advances existing committed allocations to a supplied trusted allocation boundary while excluding the pending allocation, then starts that allocation's clock at the boundary. It validates the matching reservation and refuses a month change between reservation and boundary. This is a source draft only: no scheduler calls the new API, the timestamp's trustworthy capture point and selector rollback remain unproven, same-user reservations remain blocked, and a failed multi-user ledger advance requires recovery. It applies after the preceding `monthly_quota.c` patches with `git apply --unidiff-zero`; the new format and feature must not be enabled. Static review and reverse patch applicability only; no tests or deployment.

Slurm 26 source tracing narrows the remaining transaction boundary: `select_g_job_begin` in `select/cons_tres` is a no-op, while `select_g_select_nodeinfo_set` calls `job_res_add_job`, which builds `gres_list_alloc`. The candidate's commit validation therefore cannot succeed immediately after `select_g_job_begin`; the GRES side effect occurs after the job is marked running and before `allocate_nodes`. Merely moving the commit call after that side effect is insufficient: error paths must establish rollback or isolate unknown allocation state before the job can be left pending. No such integration is enabled.

The verified target source's `gres_stepmgr_job_alloc` initializes its return value to `SLURM_ERROR` and never changes it on successful nonempty allocations; the current `job_res_add_job` ignores that return value. Merely propagating the existing value would falsely reject successful GPU allocations. The disabled `slurm26-gres-alloc-status-draft.patch` changes the non-whole-node routine's initial status to success and marks a missing requested GRES as an error, under the quota guard only. It applies with `git apply --unidiff-zero` after the base source draft. Error propagation, partial-allocation isolation, rollback and the separate whole-node routine remain unresolved; this draft is not enabled or a complete fix. Source was compared against the verified source archive; only static review and reverse patch applicability were performed, with no tests or deployment.

`slurm26-gres-propagate-status-draft.patch` adds guarded propagation of that corrected non-whole-node status through `job_res_add_job`; both the step-manager library and select plugin must be built with the same guard or normal allocations would report failure. The function may already have changed GRES, memory and CPU state when it returns an error. The scheduler currently logs a select failure but can continue, and no generation-bound isolation or rollback is connected. Consequently this does not establish successful allocation or safe recovery and neither draft may be enabled. The whole-node return path is unchanged. Only static review and reverse patch applicability were performed; no tests or deployment occurred.

`slurm26-reservation-release-draft.patch` fixes a separate draft ledger leak: a successful `RELEASE2` removed its active allocation but left its bound reservation forever. It validates owner, request, job and generation, then removes both in memory only after the durable release record; WAL replay applies the equivalent transition. It applies with `git apply --unidiff-zero` after the previous `monthly_quota.c` draft patches. This is an incompatible semantic change for any WAL containing earlier draft `RELEASE2` records; no migration has been implemented. Crucially, **the caller still lacks proof that GPU/node cleanup succeeded**, so this function remains unconnected and must not be enabled or used to refund an actual job. Static review and reverse patch applicability only; no tests or deployment.
